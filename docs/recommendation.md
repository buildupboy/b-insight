# 행정동 창업 추천 계산

자연어 조건 추출은 OpenAI에만 맡긴다. 백엔드는 추출값을 실제 Supabase 목록과 대조하며, 추천 경로에서 공공데이터 API를 호출하지 않는다. DB 조회는 `BEGIN READ ONLY`와 `SELECT`만 사용한다.

## 상권명·역 이름의 지역 연결

정확한 DB 구·동과 기존 행정동 묶음을 먼저 확인한다. 서면·서면역·서면 상권·서면역 상권은 부산진구의 부전1동·부전2동·전포1동·전포2동 중 실제 DB에 존재하는 동을 비교 범위로 사용한다. 부산진문화재단의 서면(전포·부전) 권역 안내(https://www.bsjincf.or.kr/02_new/new03_view.asp?idx=3530)와 부산시 관할 행정동 목록(https://www.busan.go.kr/bhbusanjingu/)을 참고한 서비스 분석 범위이며 정확한 상권 경계나 역 반경은 아니다. 화면의 지역 라벨에 실제 포함한 동을 표시하고 각각 독립 후보로 평가한다.

별칭도 없는 지명은 Nominatim 주소 검색을 사용한다. 요청에는 사용자가 지정한 지역명만 보내며 창업 문장·업종·선호·DB 정보는 보내지 않는다. 한국·부산 결과만 허용하고, 주소의 구와 동을 현재 DB 목록 및 기존 법정동 묶음 규칙과 대조한다. 결과가 여러 동이면 기존 지역 선택 UI를 사용한다. 외부 주소가 DB의 정확한 동 이름과 연결되지 않으면 임의로 좌표에서 동을 추정하지 않는다. 행정동 자체의 경계 판정이 아닌 검색 주소를 기준으로 한 후보 연결이다.

등록된 별칭은 네트워크 호출 없이 처리한다. 외부 검색 결과는 서버에서 24시간, 최대 128개까지 재사용하며 앱을 식별하는 User-Agent, 초당 최대 1회 요청, 5초 응답 제한을 적용한다. 외부 검색에 성공한 결과 화면에는 OpenStreetMap 저작자 표시를 제공한다. REGION_GEOCODER_URL로 동일 API 형식의 서비스 주소를 바꿀 수 있다. 참고: https://operations.osmfoundation.org/policies/nominatim/ 및 https://nominatim.org/release-docs/latest/api/Search/ . 실시간 외부 검색은 현재 실행 환경의 네트워크 제한으로 확인하지 못했으며 응답 형식과 후보 선택은 모의 응답 테스트로 검증한다.

## 지역·업종

`public.stores`의 `district_name`, `dong_name`별 전체 점포와 `industry_code`별 점포를 집계한다. 2026-11-18 확인 시 점포 157,296건 모두 구·동 이름이 있었고, 실제 구·동 조합은 206개, 업종 코드는 247개였다. 수집 기준월 컬럼은 없다.

부산 전체는 저장된 206개 조합 모두를 평가한다. 구는 해당 구의 모든 동, 정확한 동은 그 동만 평가한다. 부산 외 시·도를 명시하거나 DB에 없는 지역을 입력하면 422 오류다. 동명이 여럿이면 선택지를 제공한다. `하단동`은 DB의 단일 동이 아니므로 실제 `사하구 하단1동`(854건)과 `하단2동`(1,586건)을 각각 독립 후보로 계산한다. `OO동`이 실제 DB에서 `OO1동`, `OO2동` 등으로 분리된 경우에도 같은 규칙을 적용한다. 여러 구에 걸치면 선택지를 요청한다. `남포동`은 `중구 남포동`과 정확히 일치한다. `서면`은 아래 별칭 비교 범위를 사용하고, `센텀시티`처럼 미등록 지명은 외부 검색 주소를 실제 DB 구·동과 대조한다.

업종은 DB의 실제 코드·이름을 확인한 뒤 사용한다. 2026-11-18 `public.stores`에서 코드·이름 조합 247개가 확인됐고 코드와 이름은 1:1이었다. `미용실/헤어샵/헤어숍` → `S20701`(미용실), `카페/커피숍/커피 전문점` → `I21201`(카페), `네일숍/네일샵` → `S20703`(네일숍), `분식집` → `I21007`(김밥/만두/분식), `빵집/베이커리/제과점` → `I21001`(빵/도넛), `편의점` → `G20405`(편의점)이다. 빵집 별칭은 DB 분류에 도넛도 포함된다는 경고를 표시한다.

`한식집/한식 음식점`은 확인된 코드·이름 쌍 14개, `음식점/식당`은 식사·간이음식 코드·이름 쌍 38개를 명시적으로 검증해 묶는다. 넓은 음식점 범위에서 카페(`I21201`)와 주점(`I211` 계열)은 제외한다. 이는 DB에 부모 분류 메타데이터가 없기 때문에 확인된 현재 코드·이름 목록을 기준으로 한 보수적인 범위다. 코드명 변경 또는 새로운 하위 코드가 발견되면 자동으로 추측해 포함하지 않고 분류를 다시 확인하도록 오류를 반환한다. 점포 집계는 `industry_code = ANY($1::text[])`로 하며 한 행은 한 번만 센다. 공공데이터포털의 [소진공 상가정보 설명](https://www.data.go.kr/data/15012005/openapi.do)은 대·중·소 분류 코드 길이를 각각 2·4·6자리로 안내한다.

OpenAI는 원문 업종 표현만 추출한다. 백엔드는 정확한 DB 업종명, 검증된 동의어, 검증된 넓은 범위 순서로 매칭한다. AI가 업종을 누락하면 원문에서 검증된 업종 표현 하나를 찾았을 때만 복구한다. 원문에 `존재하지 않는 업종을 창업`처럼 명시적인 미지원 표현이 있으면 단순 업종 미입력과 구분해 DB 업종 미지원 오류를 반환한다. `음식점이나 카페`처럼 복수 업종을 명시하면 선택지를 반환하고, 선택 후 조건의 업종도 선택한 값으로 바꾼다. 업종 표현 자체가 없거나 DB와 연결되지 않으면 추천을 중단한다.

## 첫 분석의 사전 집계 읽기

프로젝트 폴더에서 npm run prepare:history를 한 번 실행하면 binsight_private.history_summary에 누적·월별 집계 JSON을 저장한다. 원본 데이터를 수정하지 않으며 원본 행 수가 중복 제거 건수와 중복 건수의 합계와 일치하는지 검증한 뒤 하나의 트랜잭션으로 교체한다. 준비 쿼리는 기존 중복 제거·날짜 검증·전체 업종 기준을 공유한다. private 스키마는 PUBLIC 접근을 허용하지 않으며 백엔드 DB 계정으로만 읽는다.

서버는 첫 분석에서도 사전 집계가 있으면 조회 두 번(존재 확인과 저장된 JSON 읽기)으로 이력을 가져온다. 원본 33만 행의 그룹 집계를 요청 경로에서 실행하지 않는다. 사전 집계가 아직 없으면 기존 10개 동 묶음 조회를 사용하므로 준비 명령을 실행하기 전에는 첫 요청 지연이 남는다. 준비 후 서버를 재시작하면 메모리 캐시도 즉시 교체된다.

원본 점포이력을 갱신한 뒤에는 npm run prepare:history를 다시 실행해야 한다. 일반 사용자 분석 요청에서는 집계를 생성하거나 갱신하지 않는다. 준비는 최초 1회와 원본 변경 시의 관리 작업이며 분석 소요 시간에 포함되지 않는다. 실제 Supabase 준비 시도는 실행 환경의 ENOTFOUND로 실패했다. 로컬 PostgreSQL에서 준비 SQL을 검증했으며 실제 첫 요청 시간은 아직 측정하지 못했다.

## 분석 조회 재사용

전체 업종 이력 집계는 서버 메모리에 5분간 보관한다. 업종과 검색 지역이 바뀌어도 같은 부산 전체 구·동 집합이면 재사용한다. DB 접속 대상이나 구·동 집합이 바뀌면 다시 조회한다. 같은 집계가 진행 중이면 동시 요청은 그 Promise를 공유한다. 실패 결과는 보관하지 않고 다음 요청에서 재시도한다. 만료 후 성공적으로 새 집계를 받기 전에는 오래된 값으로 대체하지 않는다. 서버 재시작 시 캐시는 비워지며 원본 이력 변경은 최대 5분 뒤 재조회에 반영된다.

업종별 점포 수와 이력 집계는 서로 의존하지 않아 동시에 조회한다. 캐시가 비어 있는 첫 요청에는 이력 집계가 여전히 필요하며 자연어 조건 추출과 점포 조회 비용도 남는다. 캐시 적중 시 historyQueryMs는 0으로 기록한다.

## 이력 조회 부하와 오류 처리

부산 전체의 비교 기준을 유지하면서 한 쿼리의 대상은 최대 10개 행정동으로 제한한다. 각 묶음은 중복 제거·날짜 검증 CTE를 공유하는 단일 SQL에서 누적·월별 집계를 반환한다. 같은 반복 읽기 트랜잭션 안에서 모든 묶음을 합친 다음 공통 성장성 기간과 점수를 계산한다. 묶음별로 기간이나 순위를 계산하지 않는다. statement_timeout은 쿼리당 14초, 클라이언트 query_timeout은 15초다.

실패 로그에는 단계·안전한 오류 코드·대상 동 수만 기록한다. 사용자 오류는 주소 조회 실패, 연결 실패, 인증 실패, 스키마 오류, 집계 시간 초과를 구분하며 접속 문자열·비밀번호·SQL 본문은 노출하지 않는다. 실시간 Supabase 오류는 현재 실행 환경의 ENOTFOUND로 재현하지 못했다. 단위 테스트와 로컬 PostgreSQL 실행에서 통합 쿼리의 기존 합계 일치를 검증했다.

## 현재 복원 상태

분석 결과와 상세 화면의 평균 영업기간·개업·폐업·추이는 행정동 전체 업종의 전체 기간 이력으로 복원했다. 카페 등 업종 매핑 여부와 최소 표본 조건으로 이력을 숨기지 않는다. 동일 업종 점포 수는 stores에서 선택 업종을 집계한다. 전체 업종의 안정성과 성장성을 지역 맥락 지표로 추천 점수에 반영한다. 부산 전체 후보의 이력을 먼저 조회하고 점수를 계산한 뒤 요청 지역의 상위 후보를 고른다. 안정성은 유효 폐업 표본 5건 이상의 전체 기간 평균 영업기간, 성장성은 부산 전체 이력의 마지막 관측 월을 포함한 공통 12개월의 (개업-폐업)/(개업+폐업)이며 사건 10건 이상일 때만 점수를 계산한다. 표본 부족은 점수만 제외하며 기존 카드의 누적 건수, 평균 영업기간과 전체 기간 그래프는 그대로 유지한다. API growthPeriod에 성장성 기준 기간을 보관한다. 그래프는 꺾은선 디자인을 유지하며 전체 기간 월별 데이터를 가로 스크롤로 표시한다. 추천 이유는 실제 반영된 지표만 나열하며 전체 상권의 과거 이력임을 구분한다.

아래의 동일 업종 매핑과 12개월 처리 함수는 이전 구현 참고이며 현재 추천 조회에는 사용하지 않는다.

## 이전 동일 업종 이력과 점수

추천은 부산 전체 후보의 점포 수와 동일 업종 이력을 먼저 조회하고 점수를 계산한 뒤, 요청 지역의 상위 3곳을 반환한다. 검색 지역은 표시 후보만 제한한다. 각 지표는 기존 5·95백분위 방식으로 정규화하며, 비교 가능한 값이 같거나 표본이 없으면 해당 점수는 만들지 않는다.

기본 가중치는 적합도 30, 경쟁 25, 안정성 25, 성장성 20이다. 낮은 경쟁 선호는 경쟁 40, 안정성 중요는 안정성 40, 성장성 중요는 성장성 35로 적용한다. 사용할 수 있는 지표만 합계 100%로 다시 배분한다. 경쟁 무관이면 경쟁 지표를 제외한다. 적합도는 전체 점포 수의 상업 활동 비교값이며 성공 확률이 아니다.

### 업종 매핑

실시간 Supabase 접속은 실행 환경의 DNS 오류로 확인하지 못했다. 2026-11-18 작업에서는 기존 코드·이름 목록과 로컬 SQLite commercial_history_by_dong의 실제 48개 분류 조합을 조사했다. 요청 시 현재 stores의 코드·이름도 다시 확인하며, 아래 세 필드는 앞뒤 공백만 정리한 뒤 모두 정확히 일치해야 한다. 문자열 포함 비교와 전체 업종 대체는 사용하지 않는다.

| stores 코드·이름 | majornm | minornm | upjongnm |
|---|---|---|---|
| S20701 미용실 | 서비스 | 미용실 | 미용실 |
| S20703 네일숍 | 서비스 | 네일숍 | 기타 미용업 |
| I21001 빵/도넛 | 외식 | 제과점 | 제과점업 |
| I21006 치킨 | 외식 | 치킨전문점 | 치킨 전문점 |

카페는 이력에서 커피·음료 / 비알콜 음료점업으로 합쳐져 있어 카페만 분리할 수 없다. 한식 세부 업종도 한식 일반 음식점업이라는 넓은 분류에서 분리할 수 없다. 이처럼 범위를 확인할 수 없는 업종은 데이터 부족으로 처리한다. 원본 분류가 더 세분화되거나 별도 허가 업종 자료가 확보되면 명시적 매핑을 확장한다.

### 집계와 표본

동일 업종의 부산 전체 비교 후보에서 유효 개업·폐업 사건이 있는 마지막 월을 정하고, 그 월을 포함한 공통 12개월을 모든 후보에 사용한다. 행정동별 마지막 사건일로 기간을 바꾸지 않는다. 카드의 개업·폐업은 동일 업종의 전체 기간 누적 건수를 표시한다. 꺾은선 그래프와 성장성은 공통 12개월을 사용하며, API의 periodOpenings/periodClosures로 해당 기간 건수를 별도 제공한다.

기존과 동일하게 업소명·주소·분류·상태·두 날짜의 공백을 정리하고 같은 사건 필드를 한 번만 센다. 날짜는 YYYY-MM-DD 또는 YYYYMMDD이며 실제 달력상 가능한 날짜여야 한다. 개업은 유효 인허가일, 폐업은 폐업 상태와 유효 폐업일이 모두 필요한 기록이다. 영업 중 기록의 폐업일은 폐업으로 세지 않는다.

안정성은 동일 업종의 전체 과거 폐업 이력 중 유효한 두 날짜와 폐업일 >= 인허가일을 만족한 기록의 평균 영업개월이다. 평균은 실제 일수 차이를 먼저 평균낸 뒤 365.2425/12로 나눈다. 최소 5건을 요구해 한두 건의 긴 기록에 점수가 좌우되는 것을 줄인다. 현재 영업 중 점포의 기대 생존기간이 아니다.

성장성은 공통 12개월의 (개업-폐업)/(개업+폐업)이다. 사건 합계가 10건 이상일 때만 계산해 소수 사건으로 ±100%가 되는 것을 제한한다. 두 최소값은 운영상 기준이며 통계적 유의성을 보장하지 않는다. 표본 미달이면 평균 또는 그래프·해당 점수를 데이터 부족으로 표시한다. 누적 개폐업 카드는 성장성의 최소 표본 조건과 독립적으로 확인된 전체 기간 건수를 표시한다. 내부 observedEventTrend와 eventSample에는 검증용 관측값을 유지한다. 자료가 있는 기간 내 빈 달은 0으로 채우고, 원본 이력이 없는 경우에는 0으로 표시하지 않는다.

조회는 읽기 전용 반복 읽기 트랜잭션에서 이력 집계와 월별 집계를 수행해 동일한 스냅샷을 사용한다. 상권 변화 테이블은 동일 업종 점수에 사용하지 않는다. 원본의 최신 날짜는 업종별로 다르며 과거 성장 흐름을 현재 성장률로 표현하지 않는다. 로컬 미용실 자료의 마지막 사건월은 2023-05였다.

## 응답과 시간

`POST /api/analyze`는 기존 결과 구조에 `timing`을 추가한다. 자연어 추출, 전체 DB 조회, 이력 SELECT, 상권 변화 SELECT, 점수 계산, 서버 전체 시간을 각각 밀리초로 반환한다. 부산 전체 후보의 동일 업종 이력을 먼저 조회한 뒤 점수를 계산한다. 프론트엔드에는 내부 처리 시간, 출처, 표본 수와 집계 설명을 노출하지 않는다. 상세 그래프는 기간 선택 없이 공통 12개월의 개업·폐업 꺾은선을 표시한다. 실패 응답에도 경과 시간과, 해당하는 경우 검증된 선택지·추출 조건을 포함한다. 운영 로그에는 상태와 단계별 시간만 기록하며 키·입력 문장·DB 연결 정보는 기록하지 않는다.

2026-11-18 실제 `/api/analyze` SELECT 테스트에서 하단1동 6.7초, 하단2동 3.4초, 사하구 5.1초, 부전2동 5.0초였다. 이력 집계 SELECT는 각각 0.3초, 0.5초, 2.3초, 2.1초였고 네 요청 모두 HTTP 200이었다. 세 행정동을 함께 조회한 집계의 `EXPLAIN ANALYZE` 실행 시간은 약 1.2초이며 기존 `(district_name, administrative_dong_name)` 인덱스를 사용했다. 네트워크와 서버 상태에 따라 실제 응답 시간은 변한다. `stores`에는 구·동 복합 인덱스가 없다. 향후 조회 계획을 확인한 뒤 다음 인덱스를 검토할 수 있다. 이 SQL은 이번 작업에서 실행하지 않았다.

```sql
CREATE INDEX CONCURRENTLY stores_district_dong_industry_idx
ON public.stores (district_name, dong_name, industry_code);
```
