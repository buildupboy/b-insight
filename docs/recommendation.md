# 행정동 창업 추천 계산

자연어 조건 추출은 OpenAI에만 맡긴다. 백엔드는 추출값을 실제 Supabase 목록과 대조하며, 추천 경로에서 공공데이터 API를 호출하지 않는다. DB 조회는 `BEGIN READ ONLY`와 `SELECT`만 사용한다.

## 지역·업종

`public.stores`의 `district_name`, `dong_name`별 전체 점포와 `industry_code`별 점포를 집계한다. 2026-11-18 확인 시 점포 157,296건 모두 구·동 이름이 있었고, 실제 구·동 조합은 206개, 업종 코드는 247개였다. 수집 기준월 컬럼은 없다.

부산 전체는 저장된 206개 조합 모두를 평가한다. 구는 해당 구의 모든 동, 정확한 동은 그 동만 평가한다. 부산 외 시·도를 명시하거나 DB에 없는 지역을 입력하면 422 오류다. 동명이 여럿이면 선택지를 제공한다. `하단동`은 DB의 단일 동이 아니므로 실제 `사하구 하단1동`(854건)과 `하단2동`(1,586건)을 각각 독립 후보로 계산한다. `OO동`이 실제 DB에서 `OO1동`, `OO2동` 등으로 분리된 경우에도 같은 규칙을 적용한다. 여러 구에 걸치면 선택지를 요청한다. `남포동`은 `중구 남포동`과 정확히 일치한다. `서면`, `센텀시티`는 검증된 행정동 범위가 없어 임의로 연결하지 않는다.

업종은 DB의 실제 코드·이름을 확인한 뒤 사용한다. 2026-11-18 `public.stores`에서 코드·이름 조합 247개가 확인됐고 코드와 이름은 1:1이었다. `미용실/헤어샵/헤어숍` → `S20701`(미용실), `카페/커피숍/커피 전문점` → `I21201`(카페), `네일숍/네일샵` → `S20703`(네일숍), `분식집` → `I21007`(김밥/만두/분식), `빵집/베이커리/제과점` → `I21001`(빵/도넛), `편의점` → `G20405`(편의점)이다. 빵집 별칭은 DB 분류에 도넛도 포함된다는 경고를 표시한다.

`한식집/한식 음식점`은 확인된 코드·이름 쌍 14개, `음식점/식당`은 식사·간이음식 코드·이름 쌍 38개를 명시적으로 검증해 묶는다. 넓은 음식점 범위에서 카페(`I21201`)와 주점(`I211` 계열)은 제외한다. 이는 DB에 부모 분류 메타데이터가 없기 때문에 확인된 현재 코드·이름 목록을 기준으로 한 보수적인 범위다. 코드명 변경 또는 새로운 하위 코드가 발견되면 자동으로 추측해 포함하지 않고 분류를 다시 확인하도록 오류를 반환한다. 점포 집계는 `industry_code = ANY($1::text[])`로 하며 한 행은 한 번만 센다. 공공데이터포털의 [소진공 상가정보 설명](https://www.data.go.kr/data/15012005/openapi.do)은 대·중·소 분류 코드 길이를 각각 2·4·6자리로 안내한다.

OpenAI는 원문 업종 표현만 추출한다. 백엔드는 정확한 DB 업종명, 검증된 동의어, 검증된 넓은 범위 순서로 매칭한다. AI가 업종을 누락하면 원문에서 검증된 업종 표현 하나를 찾았을 때만 복구한다. 원문에 `존재하지 않는 업종을 창업`처럼 명시적인 미지원 표현이 있으면 단순 업종 미입력과 구분해 DB 업종 미지원 오류를 반환한다. `음식점이나 카페`처럼 복수 업종을 명시하면 선택지를 반환하고, 선택 후 조건의 업종도 선택한 값으로 바꾼다. 업종 표현 자체가 없거나 DB와 연결되지 않으면 추천을 중단한다.

## 점수와 제외 지표

기본 가중치는 기존 `fit=30`, `competition=25`, `stability=25`, `growth=20`을 유지한다. 명시적인 낮은 경쟁 선호일 때만 경쟁 가중치를 40으로 높인다. 값이 검증된 지표만 다시 100%로 배분한다. 적합도는 전체 점포 수를 상업 활동의 제한적인 대리 지표로 쓰고, 경쟁은 선택 업종 점포 비중을 역방향 비교한다. 매출·인구·수요로 해석하지 않는다. 단일 동은 실제 점포 수만 반환하고 상대평가 점수는 `null`이다. 비교 가능한 점수 지표가 둘 미만이어도 점수는 `null`이다.

점수 구성 요소는 검색 범위의 후보들 사이에서 5·95 백분위 값을 기준으로 정규화한다. 현재 실제 추천 경로에서 점수가 있는 지표는 `fit`과 `competition`뿐이므로 기본 적용 비중은 각각 55%·45%, 낮은 경쟁 선호를 명시하면 43%·57%다. 안정성·성장성 요청은 검증된 점수가 없어 기본 비중을 바꾸지 않는다. 두 후보의 지표 순서가 같으면 0점과 100점이 나올 수 있으며, 검색 범위가 달라지면 같은 동의 상대 점수도 달라질 수 있다. 점수는 창업 성공 확률이 아니다.

API의 `preferenceSummary`는 인식·적용·미반영 선호와 미반영 이유, 첫 후보의 실제 적용 가중치를 제공한다. `results[].scores`와 `results[].effectiveWeights`는 후보별 구성 점수와 가중치다. 인구밀도·거주인구·생활인구·유동인구 및 막연한 인구 요청은 서로 구분해 기록하지만 현재 DB에 해당 수치가 없으므로 점수에는 반영하지 않는다. 점포 밀집도를 인구 지표로 해석하지 않는다.

`commercial_history_by_dong`은 336,033건이며 유효한 인허가일은 323,327건, 유효한 폐업일은 149,264건이다. 두 날짜의 최신값은 모두 2023-06-01이고, 인허가일은 실제 개업일과 동일하다고 볼 수 없다. `fingerprint`는 고유하지만 주요 사건 필드 기준 중복 그룹 19개(초과 행 20개)가 있다. 현재 점포의 `industry_code`와 이력의 `majornm/minornm/upjongnm` 간 검증된 일대일 대응도 없다. 이력의 1,754건은 점포 DB에 없는 `부산진구 가야제1동` 이름으로 연결된다.

`commercial_change_by_dong`은 647건, 연결된 구·동 조합은 156개다. 121개 동에 여러 상권이 있고 `is_primary` 행도 복수일 수 있다. `boundary_reference_date`는 2026-10-01이지만 변화 지표 자체의 산정 시점을 보여 주는 별도 날짜 컬럼은 없다. `overlap_pct`의 정확한 산출 정의와 상권 평균의 동 전체 대표성은 확인되지 않았다. 두 테이블의 수치를 안정성·성장성 점수로 사용하지 않는다. 현재 public 스키마에는 이력·상권·점포 세 테이블만 있어 인구·매출·임대료 지표도 없다.

점포 데이터에는 분석 기간 필터가 없다. 화면에서 임의의 ‘최근 12개월’ 표시와 기간 입력을 제거했다. 이력은 상위 후보의 정확한 구·행정동만 SQL에서 필터링하며 DB에서 집계한 결과 행만 백엔드로 가져온다. 업소명·주소·업종 분류·상태·두 날짜의 공백을 정리한 뒤 사건 필드가 같은 행을 한 번만 센다. `fingerprint`는 원본 행 식별자이며, 영업 허가의 고유 사업체 ID는 없다. 따라서 이름·주소·날짜가 바뀐 동일 업소를 확실히 병합할 수 없고, 표시값은 **중복 사건 필드를 제거한 기록 기준**이다.

추천 카드 제목은 `개업`, `폐업`, `평균 영업기간`이다. 개업은 유효한 `apvpermymd` 건수이며 **인허가일 기준**이라고 표시한다. 폐업은 `trdstatenm='폐업'`이고 `dcbymd`가 유효한 건수다. 공백·달력상 불가능한 날짜는 제외하고 폐업일 누락·오류 건수는 별도로 반환한다. 개업·폐업의 최소·최대 관측 날짜를 각각 표시하며 건수 차이로 증가율을 계산하지 않는다. 근거 행 자체가 없으면 건수는 `null`이고, 행은 있으나 해당 유효 사건이 없으면 확인된 0건이다.

평균 영업기간은 `폐업` 상태, 유효한 인허가일·폐업일, `폐업일 >= 인허가일`을 모두 만족한 기록만 사용한다. **실제 날짜 차이 일수의 평균 ÷ (365.2425 ÷ 12)**로 개월을 계산하고 화면에서 마지막에만 소수점 한 자리로 표시한다. 유효 표본 수, 표본의 날짜 범위, 인허가일·폐업일 누락/오류 및 날짜 역전 제외 건수를 함께 제공한다. 이 값은 폐업 기록의 과거 인허가일~폐업일 평균이며, 현재 모든 점포의 기대 생존기간이 아니다. 유효 표본이 없으면 `산출 불가`다.

`stores.industry_code`와 이력의 `majornm/minornm/upjongnm` 간 공식 대응표가 확인되지 않았다. 따라서 **미용실·카페를 포함한 모든 이력 값은 행정동 전체 업종 기준**으로만 표시한다. 선택 업종의 점포 수와 분리하며 추천 점수에도 반영하지 않는다.

상권 변화 자료는 같은 구·행정동에 연결된 각 `market_id`를 개별 상권으로 표시한다. `comm_nm`, `change_indicator_nm`, `average_open_months`, `average_close_months`, `overlap_pct`, `is_primary`, `boundary_reference_date`를 참고 정보로 사용한다. 이 상권 단위 전체 업종 값은 새로 계산한 **행정동 전체 업종 폐업 기록 평균**과 분리해 표시하며, 서로 합산하거나 대체하지 않는다.

## 응답과 시간

`POST /api/analyze`는 기존 결과 구조에 `timing`을 추가한다. 자연어 추출, 전체 DB 조회, 이력 SELECT, 상권 변화 SELECT, 점수 계산, 서버 전체 시간을 각각 밀리초로 반환한다. 점수 계산을 마친 상위 3개 후보에만 이력과 상권 참고 데이터를 조회·첨부한다. 프론트엔드는 버튼 클릭부터 응답 화면 표시까지의 시간을 초 단위로 보여준다. 실패 응답에도 경과 시간과, 해당하는 경우 검증된 선택지·추출 조건을 포함한다. 운영 로그에는 상태와 단계별 시간만 기록하며 키·입력 문장·DB 연결 정보는 기록하지 않는다.

2026-11-18 실제 `/api/analyze` SELECT 테스트에서 하단1동 6.7초, 하단2동 3.4초, 사하구 5.1초, 부전2동 5.0초였다. 이력 집계 SELECT는 각각 0.3초, 0.5초, 2.3초, 2.1초였고 네 요청 모두 HTTP 200이었다. 세 행정동을 함께 조회한 집계의 `EXPLAIN ANALYZE` 실행 시간은 약 1.2초이며 기존 `(district_name, administrative_dong_name)` 인덱스를 사용했다. 네트워크와 서버 상태에 따라 실제 응답 시간은 변한다. `stores`에는 구·동 복합 인덱스가 없다. 향후 조회 계획을 확인한 뒤 다음 인덱스를 검토할 수 있다. 이 SQL은 이번 작업에서 실행하지 않았다.

```sql
CREATE INDEX CONCURRENTLY stores_district_dong_industry_idx
ON public.stores (district_name, dong_name, industry_code);
```
